# 代码扩展规则：最小变更，新增方法优先

## 核心规则
- **优先新增，避免修改**：所有功能扩展应通过 **新增方法、新增类、新增接口** 来实现，而不是直接修改已有的方法内部逻辑。
- **只能扩展，不能破坏**：保持已有方法的签名和行为不变，保证向后兼容性。
- **仅当别无选择时才能修改内部代码**：只有在现有方法存在 bug、或者新增功能必须改变原有业务逻辑且无法通过扩展实现时，才允许修改内部代码。修改时必须：
  1. 在注释中清楚说明为何必须修改
  2. 尽量保持原有逻辑结构，用最小 diff 完成修改

## 具体做法
1. **分析需求**：先理解要加入的新功能或变更，确认它是对现有功能的扩展还是修正
2. **寻找扩展点**：
   - 是否可以通过新增一个函数/方法，并在合适的地方调用它？
   - 能否通过继承、装饰器、组合等方式增加行为？
   - 对于配置性变化，能否新增一个参数（带默认值，不改变原有调用）？
3. **新增代码**：编写新方法、新模块，确保它们可独立测试
4. **集成调用**：在需要的地方以最小侵入方式加入对新代码的调用，例如在方法末尾添加对 `newMethod()` 的调用，而不修改原方法的既有逻辑
5. **如果必须修改**：
   - 保留原有代码，用条件判断分流新旧逻辑，或提取公共部分，避免大面积重写
   - 添加详细注释，标记修改原因和日期
   - 建议在这种场景下生成 "修改报告" 以记录改动

## 示例（TypeScript/React 风格）
需求：在模板 Section 组件中增加类型安全过滤，但原组件逻辑复杂且不允许直接改动。

✅ 推荐做法：
```typescript
// 原组件保持不变
const EducationSection = ({ education }: Props) => {
  // 原有渲染逻辑...
}

// 新增工具函数（可独立测试）
function safeFilter<T>(data: T[] | undefined | null, predicate: (item: T) => boolean): T[] {
  return (Array.isArray(data) ? data : []).filter(predicate);
}

// 在使用处最小侵入调用
const visibleEducation = safeFilter(education, (edu) => edu.visible);
```

❌ 不推荐做法：
```typescript
// 直接修改原有逻辑（侵入性强）
const EducationSection = ({ education }: Props) => {
  // 大量修改原有代码结构...
}
```
